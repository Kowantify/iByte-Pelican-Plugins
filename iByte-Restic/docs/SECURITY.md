# Security and unresolved risks

This is a disposable staging candidate. The security gate is **blocked**, not waived.

Latest 2026-10-16 audit supersedes historical clean PHP results below: pinned Panel now reports CVE-2026-108082 / PKSA-xmwy-rmx5-m7h4 in symfony/http-foundation. Final preview.2 Wings binary reports six findings, Restic one module-wide OpenPGP finding and helper zero. Source call-graph Wings audit still reports two Docker findings. None are suppressed. See RELEASE_HARDENING.md and hardening-composer-audit.json / hardening-final-wings-audit.txt / hardening-restic-audit.txt. Symfony's official advisory is https://symfony.com/cve-2026-108082 . Production cannot be approved using older zero-finding output.

Actual Linux race tests now cover protected router auth, symlink refusal and restore rollback, and real amd64 systemd/Docker tests cover installation/upgrade/failure rollback. They do not prove full native writer fencing, power-loss durability, arm64 runtime or distributed transaction safety. Retained file exports require current root password and a one-use signed actor-bound HTTPS grant; engine verifies mapped ownership/location and stages bounded tar/tar.gz outside game data. Final-backup preparation never evicts an old recovery point to make quota space.

Additional live HTTPS acceptance passes native scheduled backup, isolated older-snapshot restore, fresh final backup/native deletion and retained maintenance/export with actual Wings/Restic. Bootstrap inventory and completion broadcasting are mocked; the stopped labelled container is inspected by real Docker. The earlier missing-container attempt was correctly refused with "cannot prove server stopped" and never became a success mapping. These results still do not clear competing-writer safety or dependency advisories.

Installation repair is an explicit root-only native action (or trusted local CLI). It runs only reviewed additive plugin migrations, never rollback/drop or synchronous node calls. Missing-schema checks precede node mutations, preventing a forget followed by a missing-recovery-table SQL failure. Existing escrow survives repeat repair; recreating a physically missing table does not recreate its keys. Native Wings/S3 observers remain independent of missing Restic recovery tables. The small plain-text bootstrap verifies the versioned HTTPS installer/manifest against embedded pins. The verified inner installer checks executables before replacement and retains automatic rollback. It contains no binary payload or archive extraction path. Repair queues bounded background synchronization after additive schema readiness. Whole-script authenticity still relies on the reviewed distribution origin. No separate user-managed hash files or network code pipes are used.

## Dependency findings

The explicit root-admin key UI supersedes the earlier node-only/no-key-API scope below. New records preserve owner/node/server/profile/path/snapshot history independently of deleted native rows. This adds a high-value encrypted credential store: compromising Panel APP_KEY plus its database can expose retained repositories. The authenticated private recovery endpoint and explicit root reveal are the user-authorized secret-bearing exceptions; no ordinary backup/job/status response carries credentials. There is no rotation/deletion API for the vault. See RECOVERY.md and DECISIONS.md. Native Linux retained-delete/distributed concurrency and actual browser reveal still need acceptance tests.

Storage/job reporting returns counters/UUIDs only; ordinary downloads decrypt without requiring a key. Dedicated encrypted recovery escrow and explicit root reauthenticated reveal are separate privileged flows. New repositories use independent random passwords. Existing v3 shared-profile keys upgrade in two phases; previously escrowed offline/deleted repositories can retain the original shared password. Historical passwords expose older copies only where the corresponding wrapper still exists. Preserve complete repository/key files and protect downloaded kits. Early deletion/model guards and the explicit retained-delete path protect tested sequential Panel calls; raw SQL/direct daemon calls and untested distributed lifecycle races remain outside this guarantee. Shared blob usage is not exclusive/reclaimable billing; S3 physical usage remains unavailable. See RECOVERY.md and STORAGE_AND_LIFECYCLE.md.

`composer audit --locked` returned exit 0 and no advisories or abandoned dependencies for the pinned Panel lock. The initial Go binary scan of stock Wings reported 11 matches. Its conservative findings are preserved in `go-vulnerability-audit.txt` as baseline evidence, not the final patched-binary result.

An isolated dependency patch updates x/net v0.58.0 to v0.60.0 and adds its checksums. The official [HTTP/2 advisory](https://pkg.go.dev/vuln/GO-2026-6617) identifies that fixed version. No Wings handler or Panel core is rewritten for this update.

With govulncheck v1.9.0, full source scan after that fix still exits 3 on [GO-2026-4887](https://pkg.go.dev/vuln/GO-2026-4887) and [GO-2026-4883](https://pkg.go.dev/vuln/GO-2026-4883) in upstream `github.com/docker/docker@v28.5.2+incompatible`. These are unreviewed, module-wide Moby/Docker server advisories. Wings uses the Docker client; the reported traces include client APIs and package initialization. That makes applicability uncertain, **not cleared**. The Go database gives no fixed version on the existing module path. Migrating Wings to the new Moby major API would exceed the tiny patch boundary and requires upstream work and container regression tests.

No suppressions are installed. CI source scanning intentionally fails publication until these findings are resolved or upstream-reviewed applicability evidence supports an explicit decision. The first source scan with govulncheck v1.1.4 crashed on newer Go syntax; the checker was replaced with pinned v1.9.0 and the source scan completed. Compiler success and absence of a PHP advisory do not clear the overall gate.

The shipped Restic runtime is also centrally rebuilt. Scanning the original official v0.19.1 Linux binary found 34 conservative matches in its old Go toolchain/dependencies; that binary is **not** the final distributed runtime. Exact source `6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf` is built with Go 1.27.2 and a separate locked dependency patch: x/net 0.60.0, x/crypto 0.57.0, x/text 0.42.0, compression 1.20.1, gRPC 1.83.2 and OpenTelemetry 1.45.0 (plus resolver-required transitive pins). Optional self-update is omitted; upstream's `disable_grpc_modules` build tag is retained. No Restic source logic is patched. Baseline and rebuilt/source scan evidence are kept separately. Binary scans can conservatively flag unused OpenPGP/module-wide matches beyond the source call graph; those are reported, not suppressed or silently cleared. CI remains fail-closed.

Final rebuilt Restic source-reachability audit exits 0 (no called vulnerabilities; one unused module advisory). Its binary audit still exits 3 on OpenPGP `GO-2026-5932`. The final Wings binary scan reports six conservative matches (OpenPGP plus Docker); its full source call graph reports the two Docker advisories above. The node helper binary scan exits 0. These differences are preserved in evidence and require review; they are not combined into a misleading single "all clear" number.

## Operational limits

Keep node config, state, repo roots, executable and credential ancestors owned by the daemon/root and inaccessible to game processes. Never put a repository, state or password under a game volume. Do not edit node profiles while jobs run; restart Wings after reviewed profile changes. Store the generated password in a secure operator backup: losing it makes encrypted snapshots unrecoverable. Root-admin key reveal/export is explicitly reauthenticated and audited; destructive key regeneration is absent.

Backup data is crash-consistent when a game is running. Use existing native schedule command/power tasks to flush and stop applications for stronger consistency. This addon cannot guarantee database/world consistency of live game writes. Restore requires an already stopped server; it never kills or starts a game automatically.

The restore commit has a durable journal but lacks demonstrated power-loss atomicity and full Linux metadata durability testing. A failed Panel restore stays protected even after ordinary node rollback; the operator must inspect rather than assume it is healthy. Export/restore staging can consume snapshot-size space, and retained rollback trees consume the former world's space. Restic metadata and archive output limits can fail large workloads; do not hide those failures.

Native `SetRestoring` does not fence every writer. Existing JWT uploads/background pulls and privileged file API requests can bypass that flag. Production restore is blocked pending a supported Wings write-maintenance fence (including in-flight writers), not merely the proposed Panel dispatch method. This preview restore may be exercised only in isolated disposable fixtures with no competing uploads, file requests or pulls. See UPSTREAM_MAP for exact paths. No global native file-route overrides are installed.

No production secrets, private endpoints or data were used. Paymenter, webserver configuration and production services were not touched.

Explicit forced stale-record cleanup is admin-only and current-password-confirmed. It performs no node RPC/filesystem/forget/prune and preserves encrypted recovery material. Per the user's explicit override, it can remove locked, recent/pending records despite lifecycle reservations. It dismisses non-restore polling without claiming verified node deletion and retains actor/UUID/previous-lock audit. Restore protection/evidence remains; it cannot cancel live node work, repair bindings or clear node quarantine. Normal customer deletion/retention still respects locks.

Unique-key journal/history tests cover cross-server password refusal, original profile refusal on new repositories, restart-safe prepare/finalize, invalid/uncommitted escrow receipts, and real original-wrapper retirement. Latest-only lifecycle tests exercise native Delete/Transfer handlers, older locks, durable reservations, committed transfer notification and authenticated completion with HTTP/daemon mocks; distributed runtime safety is still a staging gate.

Whole-repository force deletion is a separate explicit root/password approval after an irreversible-loss warning. Node/profile/host/server identity, captured location fingerprint and protected filesystem roots remain mandatory. It intentionally overrides locks, unknown snapshots, missing markers/mappings and corrupted Restic passwords/config; no Restic listing/forget/password is needed to remove an approved local leaf. A daemon-authenticated maintenance group supports deleted/transferred source inventory without a live server lookup. Paths are never supplied by browsers/Panel. Active addon jobs are refused; unknown restore journals and protection remain. Retire before removal, preserve key/state files, and never auto-reinitialize. Physical S3 deletion is unsupported. External root writers/mount changes are outside addon serialization and must be stopped before explicit cleanup. Distributed/Linux deletion safety remains a staging gate.
